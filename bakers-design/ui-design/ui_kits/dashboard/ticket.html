Beschreibung

format: bb_rich

Die aktuelle State-Machine ist über mehrere Plugins verstreut und schwer testbar. Übergänge werden an drei Stellen validiert (presave, Form-Alter, JSON:API-Constraint) — die Logik soll in einen einzigen WorkflowTransitionValidator-Service wandern.

Akzeptanzkriterien

  • Alle erlaubten Übergänge in einer Definition (pro Workflow-Bundle).
  • done bleibt terminal — kein Rückweg nach review.
  • Ein released Run verliert den Write-Scope (403 bei späterem Write).
  • Kernel-Test deckt jede Kante ab; CI grün.

Referenz: #GL-129 (Workflow-Plugin-Architektur).

Designnotizen

Konsistenz mit dem Dashboard

Keine neuen Tokens, keine neuen Farben. Hero-Akzentkante, .pill, .lease, .dot, .ava und die Run-Tabelle sind 1:1 die Dashboard-Primitive — der Ticket-Screen ist visuell dieselbe App, nur eine Ebene tiefer.

State-Bahn = Workflow-Definition

Die Schritte spiegeln das Workflow-Bundle (feature: backlog→…→done). current trägt die Zustandsfarbe (teal=running, gelb=needs_input). done ist terminal dargestellt — kein Rückweg, passend zur State-Machine.

Strikt read-only

Reine Anzeige — keine Mutations-UI im Screen: keine Action-Buttons, kein Kommentar-Composer. Der Screen pollt nur (15 s, gleiche Ring-Animation) und spiegelt den Stand. Schreiben passiert außerhalb (Drupal-Forms / JSON:API), nicht hier.

Fragmente

Jede <section> trägt eine id="frag-*" und ein data-screen-label — je Sektion ein htmx-Fragment, das unabhängig nachladen kann (Runs/Aktivität refreshen häufiger als die Beschreibung).
