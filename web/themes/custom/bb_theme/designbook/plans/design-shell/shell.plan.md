## Decisions
Reference: none. The `reference` stage ran reference-free (`reference_dir: ""`) — no browser pass, no asset or font downloads, no baseline PNG matrix. Structure is derived from BB-327's decided information architecture and BB-330's acceptance criteria instead of from an extracted design.
Shell type: Linear-style application shell — collapsible left sidebar, top bar, content, status bar, command-palette overlay.
Root: `page` (existing component, updated — not recreated). Slots: sidebar, header, content, footer, overlay.
Navigation landmark: the sidebar, not the top bar. The top bar is named `toolbar` and the bottom bar `status_bar`; neither carries a navigation slot, and no `header`/`footer` component is created.
Navigation entries: Dashboard, Projects, My Tickets — three top-level links, in that order, each with an icon — followed by a `Workspace` group heading holding `Teams` and `Settings`. `Teams` is itself a group heading and is the one row that carries a create affordance (`[+]`, the `button` component in its `ghost` + `icon_only` variant); beneath it sits one row per team, each carrying a mark instead of an icon and a dot menu whose entry is `Team settings`. A team row has no further level. `Settings` keeps its sub-navigation one level deep as a disclosure, carrying the five pages the Settings section owns: Workspace, Groups, Projects, Teams, Labels. A group heading is a heading row, not a link — a single disclosure `<button>` spanning the row, with no `href` — and it does not indent its children; every other parent still does. This replaces BB-327's six-entry decision, which the first capture recorded here — see note 8.
Sidebar states: `expanded` and `collapsed`, driven by a `collapsed` prop and toggled through the shared js-behavior disclosure pattern. Collapsed keeps the link icons and the team marks and drops every label, so every navigation surface the expanded rail reaches stays reachable; the group heading rows, the `[+]` and the dot menus are hidden with the labels, because a 56px rail has no room for a label and a control whose target is a hidden list is a control that lies. There is exactly **one** collapse affordance — the toggle in the sidebar head, which carries `aria-expanded`/`aria-controls` and is what `sidebar.js` flips. The `actions` slot at the foot stays empty in the shell scenes; filling it with a second, unwired "Collapse sidebar" button would present one function as two controls.
Workspace switcher: top of the sidebar; carries the workspace mark, so the shell needs no separate product logo. Panel closed by default.
Search: a `search_trigger` in the toolbar, not a live input — it opens the command palette and shows the keyboard hint, so search and the palette are one surface.
Primary action: `button[variant=primary]` labelled "New ticket" with a leading `plus` icon, rendering an anchor because it carries an `href`.
User menu: `user_menu` on the right of the toolbar, using the existing `avatar` component as its trigger and a disclosed `panel` slot.
Command palette: `command_palette` fills the page `overlay` slot. Placement and component boundary only — it owns the dialog element, its open-state hook and a `content` slot, and does nothing yet.
Status bar: `status_bar` fills the page `footer` slot and carries a `refresh_indicator` (existing `status-dot` plus a relative last-refresh time).
Components (new): sidebar, navigation, workspace_switcher, toolbar, search_trigger, button, user_menu, command_palette, status_bar, refresh_indicator
Components (existing, updated): page — two new slots (`sidebar`, `overlay`) and a rewritten description replacing the Gin-era contract
Components (existing, reused unchanged): icon, avatar, status-dot
Variants: sidebar → expanded, collapsed · navigation → main, settings_open · button → primary, ghost
Scenes: `Shell` (sidebar expanded, settings sub-navigation disclosed) and `Shell collapsed`, both injecting the screen through `$content`.

## Notes
Deviations from the loaded rules and blueprints, each deliberate and confirmed by the human on 2026-08-11:

1. `shell/rules/navigation.md` binds `header` and `footer` to carry a `navigation` component as a required slot. This shell has no `header`/`footer` component: the navigation landmark is the sidebar, which owns the required `navigation` slot. The `page` slots keep the names `header` and `footer`; the components filling them are `toolbar` and `status_bar`.
2. `components/rules/layout-constraints.md` requires width control to be delegated to a `container`. An application shell is full-bleed, so there is no max-width to delegate and no `container` component is created. Nothing in the shell claims its own max-width, so the rule's actual constraint is not violated.
3. The `logo` blueprint is not used. BB-330 does not ask for a logo, and a separate product mark next to the workspace mark would be a near-duplicate, which the intake reuse rule forbids.
4. `page` is an existing component and is updated in place rather than recreated. This is required by the ticket, which names `components/page/page.component.yml` and its "Chrome is supplied by Gin; the header and footer slots stay empty" description as part of what the ticket rewrites.
5. Eleven new sprite sources are needed under `assets/icons/src/` before the scenes render correctly: dashboard, board, ticket, run, conductor, settings, search, chevron-down, chevron-right, panel-left, command. Only eight icons exist today (alert-triangle, arrow-right, eye, info-circle, lock, plus, user, x-circle) and none of them covers a navigation entry. The sprite is built by the vite spritemap plugin, so the theme build must run before Storybook shows the shell.

Corrections applied after the first replay, on human review of the rendered scenes:

6. **The Settings sub-navigation was invented, and it was wrong.** The first capture named General, Members and Projects. BB-330 never lists the Settings children, so the intake filled the gap from nothing — and contradicted the two artifacts that do own them: BB-331's `designbook/sections/settings/settings.section.scenes.yml` defines the five pages `workspace`, `groups`, `projects`, `teams`, `labels`, and BB-338 is titled after the same five. Only `projects` overlapped; "Members" is part of the Workspace page per BB-338, not a page of its own. The root cause is that BB-331's sections are not in this branch — its merge request against `feat/bb-327-design-the-bakers` is still open — so the intake had no IA to read. Whoever replays this capture reads the corrected five.
7. **The sidebar had two collapse affordances, one of them dead.** `sidebar.twig` puts the functional toggle in the head (it carries `aria-expanded`/`aria-controls`, and D7 makes those attributes the state), while the scenes additionally filled the foot `actions` slot with a `button[variant=ghost]` labelled "Collapse sidebar" that is wired to nothing. The foot filling is removed. Note this deviates from the spec handoff's wording "collapse toggle at the bottom": the functional toggle sits in the head, which is also where the Linear model this shell follows puts it.
8. **The six-entry navigation was replaced, and BB-341 is what replaced it.** This capture originally recorded BB-327's six decided entries — Dashboard, Board, Tickets, Runs, Conductors, Settings — and BB-330 built exactly that. After reviewing the rendered shell the human specified a different information architecture on 2026-08-13; BB-341 carries it, and the Navigation-entries and Sidebar-states lines above are rewritten to it. Four of the six entries were rail entries for things that turned out not to need one, and each has a named destination instead: **Board** is part of the Dashboard; **Runs** are reached as a list on the ticket detail and read as statistics on the Dashboard and the project dashboard; **Conductors** get the same statistics treatment; a workspace-wide **Tickets** list is displaced by `My Tickets` plus a project's own tickets under `Projects`; and **Settings** moves under the `Workspace` group, keeping its five pages. Nothing about the shell's landmarks, its slots or its disclosure rule changed — only which rows the rail carries, so notes 1–7 all still stand. What changed in the `navigation` contract is additive: optional `heading`, `mark`, `action`, `menu` and per-item `open` keys, two new icon sources (`project`, `more-horizontal`), and two further scenes (`Team menu open`, `Team settings`). One consequence for the Scenes line above, which is otherwise unchanged: its `Shell` parenthetical *"settings sub-navigation disclosed"* no longer describes that scene. BB-341's plan renders `Workspace` and `Teams` open and `Settings` **closed** in every sample-data file, which is what the new per-item `open` key exists to express; the disclosed Settings state is still shown, by the `settings_open` variant story, which keeps its meaning. The `board`, `run` and `conductor` icons stay in the sprite — the `property_row` and `filter-bar` stories use them for the workflow and conductor pills. Two questions this deliberately leaves open, so silence is not read as a decision: what `My Tickets` opens (recorded on BB-335) and whether the Board keeps a screen of its own (recorded on BB-334 and BB-333). **Whoever replays this capture builds the tree in the Navigation-entries line above, not the six.** The full reasoning, decision by decision, is `docs/specs/BB-341-redesign-the-sidebar-navigation.spec.md` (D1, D5–D11, D16).

Further context the schema does not capture:

- Component names use snake_case because the Designbook `Component` schema enforces `^[a-z][a-z0-9_]*$`. The existing theme mixes conventions (`board-card`, `ticket-row` vs. `auth_card`, `form_element`); the new shell components follow the schema, not the hyphenated neighbours.
- `button` is deliberately distinct from the existing `submit` component: `submit` is form-bound, `button` is the general action control and renders an anchor when `href` is set.
- The settings sub-navigation and every other open/closed state use the `js-behavior` blueprint: `aria-expanded` on the trigger, `aria-controls` pointing at the panel, the panel carrying the id and starting `hidden`, driven by a `Drupal.behaviors` + `once()` handler in a co-located `<name>.js`. The accessible attribute is the source of truth, never a CSS class.
- Colour and typography stay provisional. BB-329 removed the Gin coupling and explicitly left the final look open, and BB-327 states that visual polish is not the goal — structure first.
- The theme has no `node_modules` in this worktree; `pnpm install` and a theme build are prerequisites for rendering the scenes in Storybook.
